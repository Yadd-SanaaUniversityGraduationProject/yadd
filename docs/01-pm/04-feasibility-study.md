# دراسة الجدوى — Feasibility Study

> **الحالة:** `SKELETON — DATA REQUIRED — SYNCHRONIZED THROUGH DEC-091`
>
> لا توضع أرقام تكلفة أو ادعاءات قدرة تقنية دون دليل. هذه الوثيقة تميز بين الاتجاهات المعتمدة والخيارات التقنية التفصيلية التي ما تزال تحتاج تحققًا.

## 1. Economic Feasibility

### البيانات المطلوبة
- تكلفة الاستضافة/الخادم في سيناريو MVP.
- نسخة/ترخيص SQL Server المستهدف في سيناريو التطوير والتشغيل وتكلفته إن وجدت؛ لا يفترض أن تكلفة بيئة التطوير تمثل تكلفة تشغيل إنتاجي.
- نسخة/ترخيص SQL Server المستهدف في سيناريو التطوير والتشغيل وتكلفته إن وجدت؛ لا يفترض أن تكلفة بيئة التطوير تمثل تكلفة تشغيل إنتاجي.
- تكلفة التخزين والوسائط والإشعارات وأي خدمة خارجية لازمة.
- تكلفة مزودات OCR/Face/Liveness/Moderation المقترحة إن استخدمت.
- تكلفة النشر/الاختبار والأجهزة المتاحة للفريق.
- مدة الاشتراك معتمدة 30 يومًا؛ السعر النهائي فقط ما يزال مفتوحًا ضمن `SUB-PLAN-Q01`.
- وسائل وإجراءات الدفع الخارجي للاشتراك وإثباته ما تزال مفتوحة عبر `SUB-PAY-Q01`.

### الحالة الحالية
- نموذج الإيراد القائم على اشتراك دوري للمقدمين دون عمولة معاملات معتمد كـBusiness Model وفق DEC-021.
- يدير YADD سجل الاشتراك، بينما التحصيل خارجي ويؤكده موظف مخول وفق DEC-042/043.
- لا تعني هذه القرارات أن الجدوى الاقتصادية مثبتة؛ ما تزال التكلفة والإيراد والتشغيل بحاجة بيانات وتحليل فعلي.

### المخرج المطلوب
جدول تكلفة تقديرية موثق + تفسير لماذا النطاق المختار مناسب لمشروع التخرج، دون اختلاق أسعار أو عوائد.

## 2. Technical Feasibility

### اتجاهات معتمدة
- Architecture Client–Server مع Backend/API مركزي كمرجع نهائي لقواعد العمل والصلاحيات — DEC-065.
- واجهة Web هي الواجهة الأساسية الحالية — DEC-065.
- Flutter اتجاه معتمد لعميل Mobile لاحق يتصل بالـAPI نفسه — DEC-065.
- AI-assisted Service Provider Identity Verification وTrust & Safety داخل نطاق MVP، مع Human Review للقرارات الحساسة — DEC-037..040/085.
- Stack التنفيذ المعتمد: ASP.NET Core (MVC + Web API) + Entity Framework Core + Microsoft SQL Server + ASP.NET Core Identity — DEC-091.
- Authentication direction: Cookies للWeb وJWT Bearer لعميل Flutter/API — DEC-091.
- AI integration direction: External APIs خلف Service/Integration Layer، مع بقاء المزود والسياسات التفصيلية مفتوحة — DEC-091.

### خيارات/تفاصيل ما تزال `PROPOSED / NEEDS VERIFICATION`
- الإصدارات التنفيذية الدقيقة والمتوافقة للحزم قبل بدء البرمجة، مع مراجعة دورة الدعم والتوافق بين ASP.NET Core وEF Core وSQL Server.
- مزود/مزودو OCR/Face/Liveness/Moderation — `AI-PROV-Q01`.
- بنية التكامل الدقيقة مع خدمات AI وتكلفتها وسياسة الاحتفاظ بالنتائج.
- تفاصيل الاستضافة والتخزين والأمن التشغيلي ومزود SMS؛ سياسة القنوات نفسها معتمدة في DEC-090.

### أسئلة التقييم
- خبرة الفريق الفعلية بكل تقنية مرشحة.
- قابلية إنجاز Core flows ضمن الوقت والموارد المتاحة.
- أثر الاتصال المتقطع أو المحدود على Web/Mobile/API flows.
- حجم تخزين الوسائط وآلية إدارتها.
- متطلبات الخصوصية والأمن، خصوصًا بيانات الهوية والوجه والمحادثات.
- اعتماديات الخدمات الخارجية ومخاطر تعطلها/تكلفتها.

## 3. Operational Feasibility

يلزم التحقق ميدانيًا من:
- قدرة المستخدم المستهدف على إنشاء طلب/استجابة/فاتورة بسهولة.
- وضوح الانتقال بين Beneficiary وProvider capabilities في الحساب نفسه.
- فهم Provider Type الحصري (`SERVICE` أو `PRODUCT`) والتصنيفات المتعددة داخله وفق DEC-074/076.
- توفر هاتف واتصال ملائمين.
- وضوح المصطلحات والأسعار والتقييمات.
- قبول Identity Verification لمقدمي الخدمات؛ Product Providers لا يطلب منهم Government ID في MVP — DEC-085.
- أثر Expired على المعاملات الجارية وبدء التعاملات الجديدة حُسم في DEC-086؛ بقي فقط أثره على الظهور العام في البحث.

## 4. Academic Validity vs Engineering Feasibility

### Academic Validity
يمكن توثيق اتجاهات النظام المعتمدة ومتطلبات التصميم الحالية للمناقشة الأولية، لكن لا يجوز تقديم هذه الوثيقة كدليل أن المشروع «مجدٍ» قبل استكمال بيانات الجدوى المطلوبة.

### Engineering Feasibility
قابلية التنفيذ الفعلية لفريق المشروع خلال الوقت والموارد المتاحة ما تزال `NEEDS_VERIFICATION` حتى مراجعة الخبرات والتقنيات والتكاليف والاعتماديات الخارجية والنطاق التنفيذي.

## 5. قرار الجدوى

لا يوضع `FEASIBLE` حتى تملأ البيانات السابقة وتراجع من الفريق. النتيجة الحالية: `NEEDS_VERIFICATION`.
