# Software Requirements Specification — YADD MVP

> **الإصدار:** v0.6
>
> **الحالة:** `PARTIALLY ANALYZED — NOT BASELINED`
>
> تم اعتماد نموذج الحساب، نموذج نشاط المقدم، الموقع والمطابقة الجغرافية، التحقق الرسمي من المقدم، ووظائف AI الأساسية للثقة والسلامة، إضافة إلى جزء جوهري من تدفق المعاملات. البنود المفتوحة موضحة صراحة ولا تعتبر متطلبات نهائية.

## 1. Scope

مرجع النطاق: `00-project-baseline.md` وDecision Register.

## 2. Account / Portal Model — Approved

مرجع القرار: `DEC-008..DEC-011` و`14-account-portal-model.md`.

- يوجد حساب `User` واحد للشخص.
- اختيار «مستفيد» أو «مقدم» يحدد بوابة البداية وليس نوع الحساب الدائم.
- يحتاج استخدام بوابة المقدم إلى `Provider Profile` داخل الحساب نفسه.
- يمكن الانتقال بين البوابتين بالحساب نفسه، لكن وظائف التقديم لا تعمل قبل تحقق Provider المعتمد.

## 3. Provider Activity Model — Approved

مرجع القرار: `DEC-029/030` و`19-provider-activity-model.md`.

- يمتلك الحساب Provider Profile واحدًا كحد أقصى.
- يمكن تفعيل `Service Activity` أو `Product Activity` أو كليهما.
- لا يؤدي تفعيل النشاط الثاني إلى إنشاء حساب أو Provider Profile جديد.
- الهوية وحالة Provider Verification مشتركتان على مستوى Provider Profile.
- بيانات ومسارات الخدمات والمنتجات يمكن أن تختلف حسب طبيعة النشاط.

## 4. Location & Neighborhood Model — Approved

مرجع القرار: `DEC-031..DEC-033` و`20-location-and-neighborhood-model.md`.

- يحدد المستفيد موقع الطلب بالمديرية والحي.
- لا يظهر العنوان الدقيق أو إحداثيات GPS في الطلب العام.
- يمكن للمستفيد مشاركة موقع أدق داخل Transaction Chat بعد اختيار مقدم وعند الحاجة.
- يحدد المقدم المديريات/الأحياء التي يستطيع خدمتها.
- يبدأ توزيع الطلب داخل حي الطلب نفسه، ثم يمكن توسيعه إلى أحياء مجاورة عند عدم كفاية الاستجابات.
- تعرف الأحياء المجاورة بقائمة علاقات جوار مُدارة داخل YADD في MVP، وليس بحساب GPS Radius كأساس للأهلية.
- القائمة الفعلية الحالية للأحياء والجوار تحتاج `LOC-DATA-Q01`، وعتبة/زمن التوسع تحتاج `LOC-OPS-Q01`.

## 5. Provider Verification Model — Approved

مرجع القرار: `DEC-034..DEC-036` و`21-provider-verification-model.md`.

- كل Provider Profile يحتاج تحققًا رسميًا قبل تفعيل وظائف التقديم.
- الحد الأدنى المعتمد: وثيقة هوية رسمية وصورة شخصية مع الوثيقة، مع بيانات الحساب اللازمة للمطابقة.
- لا يتم التفعيل تلقائيًا بعد الرفع.
- القرار النهائي بالتفعيل أو طلب إعادة التقديم أو الرفض يصدر من موظف YADD مخول.
- يمكن للذكاء الاصطناعي تنفيذ فحوص مساعدة، لكن نتيجته لا تفعّل أو ترفض الحساب وحدها.
- بيانات وصور التحقق حساسة وغير عامة وتخضع لصلاحيات وصول وتدقيق.
- أنواع الوثائق ومدة الاحتفاظ والتراخيص المهنية الخاصة تبقى أسئلة فرعية مفتوحة.

## 6. AI Trust & Safety Model — Approved

مرجع القرار: `DEC-037..DEC-040` و`22-ai-trust-safety-model.md`.

وظائف AI الأساسية المعتمدة للـMVP هي:

1. دعم Provider Verification في الخلفية، مثل OCR وفحص جودة الوثيقة ومطابقة البيانات/الوجه وLiveness عند توفر مدخل حي مناسب ومؤشرات التكرار/الاحتيال.
2. فحص النصوص والصور والأنشطة التجارية داخل YADD وفق سياسة المحتوى والأنشطة، وإنتاج Risk Flags/درجات مخاطر.

- AI لا يصدر أحكامًا دينية أو قانونية مستقلة.
- العقوبات النهائية الحساسة والحالات غير الواضحة تحتاج مراجعة بشرية.
- تستخدم Rules/Regex للحالات الحتمية البسيطة عندما تكون أنسب من AI.
- مزودو AI والعتبات التفصيلية والسياسة التفصيلية للمحتوى لم تعتمد بعد.

## 7. Actors

- `Beneficiary`: المستخدم عند البحث أو إنشاء طلب أو اختيار مقدم أو اعتماد الفاتورة أو التقييم — `ANALYZED_APPROVED`.
- `Service Provider`: Provider Profile مفعّل له Service Activity ومجتاز للتحقق — `ANALYZED_APPROVED`.
- `Product Provider`: Provider Profile مفعّل له Product Activity ومجتاز للتحقق — `ANALYZED_APPROVED`.
- قد يحمل Provider Profile النشاطين معًا — `ANALYZED_APPROVED`.
- `Verification Reviewer`: موظف YADD مخول بمراجعة طلبات Provider Verification واتخاذ القرار النهائي — `ANALYZED_APPROVED` في أصل الدور.
- `Content Moderator`: موظف/مشرف YADD مخول بمراجعة Flags والمحتوى والحالات الحساسة — `ANALYZED_APPROVED` في أصل الدور؛ تفاصيل الصلاحيات ومسار الاعتراض تحتاج استكمالًا.
- `Platform Administrator`: الدور الإداري الأوسع ما يزال `PARTIALLY_ANALYZED` حتى استكمال السياسات والصلاحيات.

## 9. Functional Requirements

### Account / Portal
- `FR-001` `ANALYZED_APPROVED`: يدير النظام حساب User واحدًا للشخص.
- `FR-001A` `ANALYZED_APPROVED`: يسمح باختيار بوابة البداية: مستفيد أو مقدم دون تثبيت نوع الحساب.
- `FR-001B` `ANALYZED_APPROVED`: يسمح بالانتقال بين البوابتين بالحساب نفسه عند استيفاء شروط البوابة.
- `FR-002` `ANALYZED_APPROVED`: يسمح بإنشاء وإدارة Provider Profile مرتبط بالحساب.
- `FR-002A` `ANALYZED_APPROVED`: لا تتاح وظائف التقديم الكاملة قبل وصول Provider Profile إلى حالة Verified.
- `FR-002B` `ANALYZED_APPROVED`: يسمح Provider Profile بتفعيل Service Activity أو Product Activity أو كليهما.
- `FR-002C` `ANALYZED_APPROVED`: لا ينشئ تفعيل النشاط الثاني حسابًا أو Provider Profile جديدًا.

### Provider Verification
- `FR-VER-01` `ANALYZED_APPROVED`: يسمح النظام للمستخدم بإرسال طلب Provider Verification مرتبط بـProvider Profile.
- `FR-VER-02` `ANALYZED_APPROVED`: يتطلب الطلب في الحد الأدنى وثيقة هوية رسمية وصورة شخصية مع الوثيقة، مع بيانات الحساب اللازمة للمطابقة.
- `FR-VER-03` `ANALYZED_APPROVED`: يدعم الطلب حالات `Draft`, `Submitted`, `UnderReview`, `Verified`, `ResubmissionRequired`, `Rejected` في المستوى المفاهيمي.
- `FR-VER-04` `ANALYZED_APPROVED`: يسمح لموظف التحقق المخول بمراجعة الوثائق والنتائج المساعدة واتخاذ قرار التفعيل/إعادة التقديم/الرفض.
- `FR-VER-05` `ANALYZED_APPROVED`: عند إعادة التقديم أو الرفض يستطيع الموظف تسجيل سبب/ملاحظة للمستخدم.
- `FR-VER-06` `ANALYZED_APPROVED`: لا يؤدي أي AI Score أو Flag وحده إلى Verified أو Rejected نهائيًا.
- `FR-VER-07` `PROPOSED/BLOCKED BY VER-DOC-Q01`: أنواع الوثائق المقبولة والجوانب/الصور المطلوبة لكل نوع تحدد لاحقًا.
- `FR-VER-08` `PROPOSED/BLOCKED BY VER-LIC-Q01`: التحقق من تراخيص مهنية إضافية لفئات محددة لم يعتمد بعد.

### Discovery / Location
- `FR-003` `ANALYZED_APPROVED`: يسمح النظام بالبحث المباشر عن مقدمي النشاط باستخدام التصنيف والمديرية/الحي.
- `FR-003A` `ANALYZED_APPROVED`: يبدأ النظام المطابقة الجغرافية بحي الطلب، ويمكن أن يوسعها إلى الأحياء المجاورة المعرفة داخل بيانات YADD عند عدم كفاية الاستجابات.
- `FR-003B` `ANALYZED_APPROVED`: لا يعتمد النظام في MVP على GPS Radius كقاعدة أساسية لتحديد أهلية المقدم الجغرافية.
- `FR-003C` `ANALYZED_APPROVED`: يسمح للمقدم بتحديد مديريات/أحياء الخدمة التي يستطيع تغطيتها.
- `FR-003D` `PROPOSED/BLOCKED BY LOC-DATA-Q01`: تعتمد قائمة الأحياء الحالية وعلاقات الجوار بعد التحقق المحلي/الإداري.
- `FR-003E` `PROPOSED/BLOCKED BY LOC-OPS-Q01`: تحدد عتبة/زمن التوسع من حي الطلب إلى الأحياء المجاورة لاحقًا.

### Request Creation / Expiry
- `FR-005` `ANALYZED_APPROVED`: يسمح للمستفيد بإنشاء طلب خدمة أو منتج مع فئة ووصف ومديرية وحي.
- `FR-005A` `ANALYZED_APPROVED`: يسمح بإضافة صور ومعلومات توضيحية للطلب بصورة اختيارية.
- `FR-005B` `ANALYZED_APPROVED`: يسمح بإضافة سعر استرشادي اختياري للطلب، ولا يعتبر السعر ملزمًا للمقدم.
- `FR-005C` `ANALYZED_APPROVED`: يحدد صاحب الطلب مدة صلاحيته عند النشر، ويصبح Expired عند انتهائها دون اختيار مقدم.
- `FR-005D` `ANALYZED_APPROVED`: يسمح بإلغاء الطلب/المعاملة قبل إرسال الفاتورة دون سبب إلزامي، مع سبب اختياري.
- `FR-005E` `ANALYZED_APPROVED`: لا يعرض النظام العنوان الدقيق أو GPS للمستفيد ضمن الطلب العام.
- `FR-006` `ANALYZED_APPROVED`: يعرض/يوصل الطلب للمقدمين الذين لديهم النشاط المناسب والمنطقة المؤهلة وفق نموذج الحي/الجوار المعتمد.

### Provider Response / Selection / Communication
- `FR-007` `ANALYZED_APPROVED`: يسمح للمقدم المتحقق والمؤهل بالاستجابة لطلب مفتوح.
- `FR-007A` `ANALYZED_APPROVED`: يسمح للمقدم بقبول السعر الاسترشادي أو إدخال سعر مقترح مختلف.
- `FR-007B` `ANALYZED_APPROVED`: في طلب المنتج يستطيع المقدم تحديد أن العربون مطلوب قبل بدء التنفيذ/التجهيز.
- `FR-008` `ANALYZED_APPROVED`: بعد اختيار المقدم يوفر النظام Transaction Chat مرتبطًا بالمعاملة لمناقشة السعر والتفاصيل وتبادل النصوص والصور/المرفقات اللازمة.
- `FR-008A` `ANALYZED_APPROVED`: يحتفظ النظام بسجل المحادثة المرتبط بالمعاملة للرجوع إليه عند النزاع وفق سياسة الخصوصية والاحتفاظ.
- `FR-008B` `ANALYZED_APPROVED`: يسمح Transaction Chat بمشاركة موقع أدق/Pin من المستفيد إلى المقدم المختار عند الحاجة، دون جعله عامًا لبقية المقدمين.
- `FR-009` `ANALYZED_APPROVED`: يسمح للمستفيد باختيار استجابة مقدم واحدة للمتابعة.

### External Payment / Fulfillment Boundaries
- `FR-EXT-01` `ANALYZED_APPROVED`: لا ينشئ النظام Payment Transaction ولا ينفذ تحويلًا ماليًا بين المستفيد والمقدم.
- `FR-EXT-02` `ANALYZED_APPROVED`: يسمح للمقدم بعرض وسائل الدفع التي يقبلها كمعلومات فقط.
- `FR-EXT-03` `ANALYZED_APPROVED`: في معاملات المنتجات يسمح بتحديد الاستلام من المقدم أو توصيل يرتبه المقدم خارج YADD.
- `FR-EXT-04` `ANALYZED_APPROVED`: يسمح بإدراج تكلفة التوصيل التي رتبها المقدم كبند في الفاتورة.
- `FR-EXT-05` `PROPOSED/BLOCKED BY DEP-Q01`: تحديد ما إذا كان النظام يسجل قيمة العربون المتفق عليها أم مجرد كونه مطلوبًا.

### Invoice / Transaction Closure
- `FR-010` `ANALYZED_APPROVED`: يسمح للمقدم بإنشاء فاتورة رقمية مرتبطة بالمعاملة بعد التنفيذ/التجهيز.
- `FR-010A` `ANALYZED_APPROVED`: تملأ هوية طرفي المعاملة في الفاتورة من الحسابات المرتبطة ولا تعتمد على إدخال اسم حر لكل مرة.
- `FR-010B` `ANALYZED_APPROVED`: تحتوي الفاتورة على بنود وأسعار وإجمالي، ويمكن أن تحتوي على صور/إثباتات اختيارية.
- `FR-011` `ANALYZED_APPROVED`: يرسل النظام الفاتورة للمستفيد للمراجعة، ويسمح له بالاعتماد أو طلب تعديل مع ملاحظة.
- `FR-011A` `ANALYZED_APPROVED`: يحتفظ النظام بتاريخ نسخ الفاتورة والتعديلات.
- `FR-011B` `ANALYZED_APPROVED`: يعرض النظام تحذيرًا صريحًا قبل اعتماد الفاتورة بأن الاعتماد نهائي داخل YADD وغير قابل للتراجع أو التعديل.
- `FR-011C` `ANALYZED_APPROVED`: عند استمرار الخلاف قبل الاعتماد يمكن رفع شكوى مرتبطة بالمعاملة إلى إدارة YADD.
- `FR-012` `ANALYZED_APPROVED`: عند الاعتماد النهائي تحفظ الفاتورة في سجل كل طرف وتغلق المعاملة داخل YADD.
- `FR-012A` `ANALYZED_APPROVED`: لا يعتبر النظام اتفاقات أو مبالغ غير موجودة في الفاتورة المعتمدة جزءًا من السجل الرسمي للمعاملة.

### Reviews / Reputation
- `FR-013` `ANALYZED_APPROVED`: لا يسمح بالتقييم إلا لطرف شارك في معاملة مغلقة بفاتورة معتمدة.
- `FR-014` `ANALYZED_APPROVED`: التقييم اختياري ومتبادل ومتاح لمدة 14 يومًا بعد إغلاق المعاملة.
- `FR-014A` `ANALYZED_APPROVED`: يعمل التقييم بنظام Double-Blind حتى يرسل الطرفان تقييميهما أو تنتهي المهلة.
- `FR-014B` `ANALYZED_APPROVED`: يتكون التقييم من 1–5 نجوم مع ملاحظة نصية اختيارية.
- `FR-014C` `ANALYZED_APPROVED`: يمكن تعديل التقييم قبل نشره فقط، وبعد نشره يصبح نهائيًا.
- `FR-014D` `ANALYZED_APPROVED`: يظهر تقييم المستفيد للمقدمين المؤهلين لرؤية طلبه كمتوسط نجوم وعدد مقيمين، ولا يعرض المستفيد غير المقيم كـ0/5.
- `FR-014E` `PROPOSED/BLOCKED BY RAT-VIS-Q01`: عرض التعليقات النصية السابقة عن المستفيد للمقدمين لم يعتمد بعد.

### AI Trust & Safety
- `FR-AI-01` `ANALYZED_APPROVED`: يشغل النظام فحوص AI مساعدة على طلبات Provider Verification وفق الإمكانات المعتمدة، دون قرار آلي نهائي.
- `FR-AI-02` `ANALYZED_APPROVED`: يفحص النظام نصوصًا خاضعة لسياسة YADD مثل وصف الطلبات والأنشطة ورسائل Transaction Chat والتعليقات، ويولد Risk Flags عند الاشتباه.
- `FR-AI-03` `ANALYZED_APPROVED`: يفحص النظام الصور/المرفقات الخاضعة للسياسة مثل صور الطلب والمحادثة والمنتجات/الأعمال لاكتشاف محتوى غير مسموح أو يحتاج مراجعة.
- `FR-AI-04` `ANALYZED_APPROVED`: يفحص النظام اسم/وصف/صور النشاط التجاري أو المنتج مقابل سياسة YADD للأنشطة المسموحة والممنوعة.
- `FR-AI-05` `ANALYZED_APPROVED`: تذهب الحالات المتوسطة/غير الواضحة أو عالية الأثر إلى موظف مخول لاتخاذ القرار.
- `FR-AI-06` `ANALYZED_APPROVED`: يمكن للنظام منع/حجز محتوى مؤقتًا عند Risk Flag عالي حسب السياسة، لكن العقوبات النهائية الحساسة لا تعتمد على AI وحده.
- `FR-AI-07` `ANALYZED_APPROVED`: يستخدم النظام قواعد برمجية/Regex بدل AI عندما تكون الحالة حتمية وبسيطة وقابلة للتحديد بدقة.
- `FR-AI-08` `PROPOSED/BLOCKED BY AI-MOD-Q01`: قائمة الفئات التفصيلية للمحتوى والأنشطة الممنوعة تحتاج سياسة مستقلة.
- `FR-AI-09` `PROPOSED/BLOCKED BY AI-MOD-Q02`: عتبات الثقة والمرور/الحجز/المنع المؤقت تحدد بعد Prototype واختبار معدلات الخطأ.

### Provider Subscription
- `FR-SUB-01` `APPROVED_AS_BUSINESS_MODEL`: يعتمد نموذج YADD التجاري على اشتراك دوري من مقدمي الخدمات/المنتجات دون عمولة من قيمة معاملات المستخدمين.
- `FR-SUB-02` `PROPOSED/BLOCKED BY SUB-Q02`: تنفيذ تحصيل الاشتراك نفسه داخل MVP لم يحسم.

### Administration
- `FR-015` `PARTIALLY_ANALYZED`: يدير موظفو YADD الوظائف الإدارية وفق الصلاحيات، ومنها التحقق والمراجعة والمحتوى والمناطق حسب الدور.
- `FR-015A` `ANALYZED_APPROVED`: يحتاج النظام إلى بيانات مرجعية قابلة للإدارة للمديريات والأحياء وعلاقات الجوار المستخدمة في المطابقة الجغرافية.
- `FR-015B` `ANALYZED_APPROVED`: يسمح لموظف التحقق المخول بمراجعة Provider Verification واتخاذ القرار النهائي.
- `FR-016` `ANALYZED_APPROVED` في أصل الحاجة: يسمح لموظف/مشرف مخول بمراجعة المحتوى وAI Flags واتخاذ إجراء وفق السياسة المعتمدة.
- `FR-016A` `PROPOSED/BLOCKED BY AI-APPEAL-Q01`: مسار اعتراض المستخدم على عقوبات moderation عالية الأثر لم يعتمد بعد.

## 10. Non-Functional Requirements — Draft / Partial

- `NFR-SEC-01` `ANALYZED_APPROVED` في المبدأ: حماية بيانات الحساب والمحادثات والمرفقات والهوية وملفات التحقق وفق تصميم أمني موثق.
- `NFR-SEC-02` `ANALYZED_APPROVED`: تقيد صلاحية الوصول إلى وثائق وصور Provider Verification بالموظفين المخولين وتخضع عمليات الوصول الحساسة لسجل تدقيق.
- `NFR-SEC-03` `ANALYZED_APPROVED`: يجب حماية بيانات التحقق الحساسة أثناء النقل والتخزين، مع تحديد التفاصيل الخوارزمية/المعمارية في التصميم.
- `NFR-PRV-01` `ANALYZED_APPROVED` في المبدأ: تقليل جمع وإظهار البيانات الشخصية إلى الحد اللازم، وعدم جعل سمعة المستفيد أو موقعه الدقيق بيانات عامة.
- `NFR-PRV-02` `ANALYZED_APPROVED`: لا يعرض الموقع الدقيق للمستفيد إلا ضمن سياق المعاملة مع المقدم المختار وعند مشاركة المستفيد له.
- `NFR-PRV-03` `ANALYZED_APPROVED`: وثائق الهوية ونتائج Face/Liveness/OCR المستخدمة في التحقق ليست بيانات عامة ولا تستخدم لتدريب نماذج AI دون سياسة/أساس وموافقة واضحة.
- `NFR-AI-01` `ANALYZED_APPROVED`: لا تعامل AI Flags كإثبات قطعي للمخالفة، ويجب أن تدعم القرارات الحساسة إشرافًا بشريًا.
- `NFR-AI-02` `ANALYZED_APPROVED`: تسجل Flags وقرارات المراجعة البشرية الحساسة في Audit Trail بما يسمح بتتبع سبب الإجراء.
- `NFR-USA-01` `PROPOSED`: واجهات واضحة للفئات المستهدفة، ويحدد معيار اختبار القبول لاحقًا.
- `NFR-REL-01` `ANALYZED_APPROVED` في المبدأ: يمنع النظام إغلاق المعاملة أو فتح التقييم قبل اكتمال شروط الفاتورة المعتمدة.
- `NFR-PER-01` `NEEDS_VERIFICATION`: هدف الأداء يحدد بعد Prototype/Architecture، خصوصًا للفحوص الخارجية/AI.
- `NFR-AVL-01` `NEEDS_VERIFICATION`: متطلبات التوفر تحدد وفق البنية ونطاق مشروع التخرج.
- `NFR-LEG-01` `NEEDS_LEGAL_VERIFICATION`: مدة الاحتفاظ بوثائق الهوية والبيانات البيومترية/نتائج المطابقة وسياسات حذفها تحتاج تحققًا قانونيًا محليًا.

## 11. Out of Scope — MVP

- `OOS-01`: تنفيذ/معالجة المدفوعات بين المستفيد والمقدم، المحافظ المتكاملة، Escrow، أو أخذ عمولة من المعاملة.
- `OOS-02`: إدارة شبكة توصيل، سائقين، تتبع شحنات أو تحصيل أجور توصيل.
- `OOS-03`: التوسع خارج أمانة العاصمة في MVP.
- `OOS-04`: النقل وصيانة السيارات والورش الثقيلة.
- `OOS-05`: حسابات الشركات والمتاجر الكبرى.
- `OOS-06`: مكالمات صوتية/فيديو أو خصائص شبكة اجتماعية عامة داخل Transaction Chat.

- `OOS-08`: اعتبار Provider Verification فحص سوابق جنائية أو إثباتًا قانونيًا عامًا خارج إجراءات YADD ما لم يوجد تكامل رسمي موثق.
- `OOS-09`: السماح لـAI بإصدار حظر نهائي عالي الأثر أو قرار Provider Verification نهائي دون إشراف بشري.
