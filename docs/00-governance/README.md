# حوكمة وثائق مشروع يَد | YADD

> **الغرض:** جعل المستودع منظمًا حول مصادر حقيقة واضحة قبل استخراج/اعتماد الفصول الأكاديمية، مع بقاء ملفات الجامعة الأصلية أعلى سلطة للمتطلبات الأكاديمية.

## ترتيب القراءة

1. ملفات الجامعة الأصلية المرفقة بالمشروع — المرجع الأكاديمي الأعلى.
2. `01-university-requirements-map.md` — خريطة مشتقة لما تطلبه الجامعة وأثره على وثائقنا؛ لا تتغلب على الملفات الأصلية.
3. `02-decision-register.md` — قرارات الفريق المعتمدة وحالاتها.
4. `03-open-questions.md` — الأسئلة المفتوحة وما أغلق منها.
5. `04-document-register.md` — حالة كل مخرج مطلوب.
6. `docs/01-pm/05-work-plan.md` — الخارطة الزمنية الحالية + Closure Tracker + توزيع المسؤوليات التشغيلية.
7. `05-two-week-plan.md` — `LEGACY / SUPERSEDED` للاحتفاظ بالأثر التاريخي فقط، ولا يستخدم للتنفيذ.
8. `06-readiness-checklist.md` — بوابة تمنع اعتبار التحليل/التصميم نهائيًا قبل اكتمال الأساس.

## مبدأ Single Source of Truth

- القرار الذي يغيّر معنى المشروع يوثق في Decision Register ثم تشير إليه بقية الوثائق بالرمز.
- توزيع العمل التشغيلي والجداول الزمنية يوثقان في Work Plan؛ لا يتحولان تلقائيًا إلى Scope/Requirement decisions.
- المتطلب يوثق في SRS بحسب حالته؛ وجود بند داخل SRS لا يعني تلقائيًا أنه Approved Requirement.
- قواعد العمل توثق في Business Rules ولا تعاد صياغتها بشكل متناقض في المخططات.
- المعلومات البحثية القابلة للاقتباس والتتبع ترجع إلى Source Register/Evidence Map والمصدر الأصلي المناسب.
- لا تنسب للمشروع مقابلات أو ملاحظات ميدانية للمستخدمين لم تُنفذ؛ Evidence المستخدمين الحالي هو `SUR-01`، مع Document Analysis وSimilar Systems كمصادر أخرى.
- `GOV-Q04` مغلق وفق `DEC-062`: قبل المشرف Survey-only كأداة جمع بيانات المستخدمين؛ الإجابات الشفهية لنفس الاستبيان لا تصبح Interviews مستقلة. هذا القرار لا يغير نص متطلبات الجامعة الأصلية ولا يسمح بادعاء تنفيذ أدوات لم تنفذ.
- الفصل الأكاديمي مخرج مشتق، وليس وثيقة تشغيلية لإدارة المتطلبات.
- مخرجات `DRAFT FOR PRELIMINARY DEFENSE` صالحة للمراجعة والعرض فقط، ولا تعد Baseline نهائيًا.

## قاعدة تغيير الحالة

`PROPOSED → ANALYZED → APPROVED` لا يحدث تلقائيًا. يجب أن يوجد قرار مراجعة واضح من الفريق، مع المرجع المناسب عندما يكون التغيير متعلقًا بمعنى المنتج/النطاق/المتطلبات.

أما تغييرات التنظيم والتوزيع والجدولة وتصحيح الروابط والحالات التي لا تغيّر معنى المشروع فتعامل كـ`Synchronization / Correction / Project Management Update` ولا تحتاج Team Decision جديدًا ما لم يتغير المعنى.
